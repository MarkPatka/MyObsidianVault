## Часть 1. Концептуальный обзор GitLab CI

### Ключевые понятия

**Pipeline** — это весь автоматизированный процесс, который запускается в ответ на событие (коммит, merge request, тег). Pipeline состоит из стадий, стадии — из джобов.

**Stage** — логическая группа работ. Стадии выполняются **последовательно** (build → test → deploy). Если одна стадия упала — следующие не запускаются (по умолчанию).

**Job** — атомарная единица работы: набор команд, которые выполняются в изолированном окружении. Джобы внутри одной стадии выполняются **параллельно**.

**Runner** — агент (сервер или контейнер), который физически выполняет команды джоба. Бывает:

- **Shared runner** — предоставляется GitLab, доступен всем проектам.
- **Specific/Group runner** — настраивается командой под конкретный проект или группу.
- Раннеры могут работать в разных режимах (executor): `docker`, `shell`, `kubernetes` и др. Самый распространённый — `docker`.

---
### Принцип работы: коммит → пайплайн → результат

```
Ты делаешь git push
        │
        ▼
GitLab читает .gitlab-ci.yml из корня репозитория
        │
        ▼
GitLab создаёт Pipeline (набор стадий и джобов)
        │
        ▼
Свободный Runner подхватывает джоб
        │
        ▼
Runner поднимает Docker-контейнер с указанным image
        │
        ▼
Runner клонирует репозиторий внутрь контейнера
        │
        ▼
Выполняются команды из before_script → script → after_script
        │
        ▼
Артефакты сохраняются, контейнер уничтожается
        │
        ▼
GitLab показывает статус: ✅ passed / ❌ failed
```

Каждый джоб — это **одноразовый чистый контейнер**. Никакого состояния между джобами нет, если явно не передать артефакты или кэш.

---
### Основные компоненты `.gitlab-ci.yml`

#### `stages` — порядок стадий

```yaml
stages:
  - build
  - test
  - deploy
```

Определяет глобальный порядок выполнения. Каждый джоб ссылается на одну из этих стадий через поле `stage`.

#### `script` — команды джоба

```yaml
my-job:
  stage: build
  script:
    - echo "Hello"
    - dotnet build
```

Главное поле джоба. Список shell-команд. Выполняются одна за другой; если любая вернула ненулевой exit code — джоб считается упавшим.

#### `artifacts` — сохранение результатов

```yaml
artifacts:
  paths:
    - bin/Release/
  expire_in: 1 week
```

Файлы, которые GitLab сохраняет после завершения джоба и делает доступными для скачивания или для последующих джобов. Без `artifacts` файлы теряются вместе с контейнером.

#### `cache` — ускорение повторных запусков

```yaml
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - .nuget/
```

Кэш сохраняется между **запусками пайплайна** (в отличие от артефактов, которые живут внутри одного пайплайна). Используется для зависимостей (NuGet-пакеты, npm node_modules), чтобы не скачивать их каждый раз.

#### `variables` — переменные окружения

```yaml
variables:
  DOTNET_ENV: "Release"
  BUILD_DIR: "src/MyService"
```

Объявляются глобально (для всего пайплайна) или локально (в конкретном джобе). Также можно задавать в интерфейсе GitLab: Settings → CI/CD → Variables — это место для секретов (пароли, токены).

#### `rules` / `only` / `except` — условия запуска

`rules` — современный способ (рекомендуется):

```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main"'
  - if: '$CI_COMMIT_BRANCH == "dev"'
```

`only` — устаревший, но часто встречающийся способ:

```yaml
only:
  - main
  - dev
```

`except` — исключения:

```yaml
except:
  - tags
```

**Правило:** используй `rules` в новых пайплайнах. `only/except` не смешивай с `rules` в одном джобе — это вызовет ошибку.

#### `tags` — выбор раннера

```yaml
tags:
  - docker
  - linux
```

Если у вашей команды есть конкретные раннеры (например, с тегом `dotnet-runner`), именно через `tags` джоб попадёт на нужный агент. Без `tags` джоб попадёт на любой доступный shared runner.

#### `before_script` и `after_script`

```yaml
default:
  before_script:
    - echo "Настройка окружения перед каждым джобом"

my-job:
  before_script:
    - echo "Этот before_script переопределяет глобальный"
  script:
    - dotnet build
  after_script:
    - echo "Выполняется всегда, даже если script упал"
```

`before_script` — подготовка (настройка, аутентификация). `after_script` — очистка (всегда выполняется, даже при падении). Локальный `before_script` полностью **заменяет** глобальный, а не дополняет.

#### `extends` — наследование конфигурации

```yaml
.base-dotnet:             # Точка в начале = скрытый шаблон (не запускается сам по себе)
  image: mcr.microsoft.com/dotnet/sdk:10.0
  cache:
    paths:
      - .nuget/

build-job:
  extends: .base-dotnet   # Наследует image и cache
  stage: build
  script:
    - dotnet build
```

Позволяет не дублировать код. Очень полезно при нескольких похожих джобах.
#### `when` — когда запускать джоб

| Значение     | Поведение                                                    |
| ------------ | ------------------------------------------------------------ |
| `on_success` | (по умолчанию) запускается, если предыдущие стадии прошли    |
| `on_failure` | запускается только если что-то упало (например, уведомление) |
| `always`     | запускается всегда                                           |
| `manual`     | требует ручного нажатия кнопки в UI                          |
| `never`      | никогда не запускается (используется в rules)                |

```yaml
notify-on-fail:
  stage: .post
  when: on_failure
  script:
    - echo "Сборка упала!"
```

#### `needs` — параллельность без ожидания стадий

```yaml
deploy-job:
  stage: deploy
  needs:
    - build-job    # Не ждёт всей стадии test, стартует как только build-job готов
  script:
    - ./deploy.sh
```

По умолчанию джоб ждёт завершения **всей предыдущей стадии**. `needs` позволяет запустить джоб сразу, как только нужные ему конкретные джобы завершились — это ускоряет пайплайн.

## Часть 2. Пошаговое руководство по написанию `.gitlab-ci.yml`

### Базовый синтаксис

`.gitlab-ci.yml` — это обычный YAML. Критически важные правила:

```yaml
# Отступы — ТОЛЬКО пробелы, не табы. Стандарт — 2 пробела.

# Строки-ключи пишутся без кавычек:
stage: build

# Строки-значения с переменными или спецсимволами — в кавычках:
image: "mcr.microsoft.com/dotnet/sdk:10.0"

# Списки — дефис + пробел:
script:
  - dotnet restore
  - dotnet build

# Вложенность — отступ относительно родителя:
artifacts:
  paths:
    - bin/
  expire_in: 7 days
```

**Совет:** перед коммитом проверяй синтаксис в GitLab: CI/CD → Editor (там есть встроенный валидатор и визуализатор пайплайна).

### Алгоритм создания пайплайна

```
Шаг 1. Определи, что нужно автоматизировать
        └── Сборка? Тесты? Деплой? → только build

Шаг 2. Определи стадии и порядок
        └── stages: [build]

Шаг 3. Для каждой стадии — определи джоб:
        └── Какой образ Docker нужен? (.NET 10 → mcr.microsoft.com/dotnet/sdk:10.0)
        └── Какие команды выполнить? (dotnet restore, dotnet build)
        └── Что сохранить как артефакт? (bin/Release/)
        └── При каких условиях запускать? (ветки main и dev)

Шаг 4. Добавь кэш для зависимостей
        └── NuGet-пакеты кэшировать по ключу ветки

Шаг 5. Проверь в GitLab CI Lint (CI/CD → Editor → Validate)

Шаг 6. Закоммить и наблюдать за первым запуском
```

### Что обязательно учесть

**Docker-образ:** Для .NET 10 используй официальный образ Microsoft. Есть два варианта:

- `mcr.microsoft.com/dotnet/sdk:10.0` — содержит компилятор, CLI, всё для сборки. **Используй для CI.**
- `mcr.microsoft.com/dotnet/aspnet:10.0` — только runtime, для продакшн-контейнеров. Для CI не подходит.

**Артефакты vs кэш:**

- **Кэш** (.nuget/, node_modules/) — ускоряет запуски, не гарантированно доступен, можно потерять.
- **Артефакты** (bin/Release/) — гарантированно сохраняются, передаются между джобами, хранятся на сервере GitLab.

**Переменные окружения:**

- Секреты (пароли, ключи API) — **никогда в .gitlab-ci.yml**. Только через Settings → CI/CD → Variables с флагом `Masked`.
- Обычные настройки — можно прямо в файле.

**Путь к `.csproj`:** Если в репозитории несколько проектов — указывай явный путь: `dotnet build src/MyService/MyService.csproj`.

## Часть 3. Шаблон пайплайна с одной стадией `build`

```yaml
# ─────────────────────────────────────────────
# .gitlab-ci.yml — минимальный build-пайплайн
# для .NET 10 микросервиса
# ─────────────────────────────────────────────

# [1] Глобальный список стадий.
# Порядок здесь определяет порядок выполнения.
# Сейчас только одна стадия.
stages:
  - build

# [2] Кэш NuGet-пакетов.
# Определён глобально — применится ко всем джобам.
# key: разные ветки получат разный кэш.
# paths: папка, куда dotnet скачивает пакеты (переопределена через переменную ниже).
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - .nuget/

# [3] Глобальные переменные.
# NUGET_PACKAGES — говорит dotnet класть пакеты в .nuget/ (внутри рабочей папки),
# чтобы кэш GitLab мог их подхватить.
# DOTNET_CONFIGURATION — конфигурация сборки (Release или Debug).
variables:
  NUGET_PACKAGES: "${CI_PROJECT_DIR}/.nuget"
  DOTNET_CONFIGURATION: "Release"

# ─────────────────────────────────────────────
# JOB: build-service
# ─────────────────────────────────────────────
build-service:

  # [4] Стадия, к которой принадлежит этот джоб.
  stage: build

  # [5] Docker-образ, в котором будет выполняться джоб.
  # sdk:10.0 содержит dotnet CLI, компилятор и всё необходимое для сборки.
  # Тег без суффикса (-alpine, -bookworm) = стандартный образ на базе Debian.
  image: mcr.microsoft.com/dotnet/sdk:10.0

  # [6] Условия запуска джоба (современный синтаксис rules).
  # Джоб запускается ТОЛЬКО при пуше в ветки main или dev.
  # На остальных ветках и в MR — молчит.
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_BRANCH == "dev"'

  # [7] Команды джоба — выполняются последовательно.
  # Если любая вернёт ненулевой exit code — джоб упадёт.
  script:
    # Восстановить NuGet-зависимости.
    # --no-cache отключает глобальный кэш dotnet (мы управляем им сами через NUGET_PACKAGES).
    - dotnet restore src/MyService/MyService.csproj

    # Собрать проект.
    # -c — конфигурация (Release).
    # --no-restore — не восстанавливать повторно (уже сделали выше).
    # -o — папка для выходных файлов (артефактов).
    - dotnet build src/MyService/MyService.csproj
        -c ${DOTNET_CONFIGURATION}
        --no-restore
        -o build/output

  # [8] Артефакты — файлы, которые GitLab сохранит после джоба.
  # paths — что сохранить.
  # expire_in — сколько хранить (потом удалится автоматически).
  # when: on_success — сохранять только при успешной сборке.
  artifacts:
    paths:
      - build/output/
    expire_in: 3 days
    when: on_success
```

### Разбор каждого блока

| Блок                   | Зачем                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `stages: [build]`      | Говорит GitLab: у нас одна стадия. Без этого джоб попадёт в стадию `test` по умолчанию.                      |
| `cache: .nuget/`       | NuGet-пакеты не скачиваются заново при каждом запуске. На медленном интернете экономит минуты.               |
| `NUGET_PACKAGES`       | Без этой переменной dotnet кладёт пакеты в `~/.nuget` — вне рабочей директории, кэш GitLab их не увидит.     |
| `image: sdk:10.0`      | Чистый контейнер с .NET 10 SDK. Именно SDK, не runtime.                                                      |
| `rules`                | Без условий джоб запускался бы на каждом коммите в любую ветку.                                              |
| `dotnet restore`       | Явный restore позволяет лучше контролировать кэш и видеть ошибки зависимостей отдельно от ошибок компиляции. |
| `--no-restore` в build | Не делать двойную работу.                                                                                    |
| `-o build/output`      | Все скомпилированные файлы окажутся в одной предсказуемой папке.                                             |
| `artifacts: paths`     | Без этого результат сборки исчезнет вместе с контейнером.                                                    |
### Быстрая адаптация под проект

Замени два значения под свой проект:

```yaml
# Если .csproj лежит в корне:
- dotnet restore MyService.csproj

# Если структура другая — укажи реальный путь:
- dotnet restore path/to/YourService/YourService.csproj
```

## Часть 4. Чек-лист для самостоятельного создания пайплайна

### Вопросы, которые нужно задать себе

- [ ] Где находится .csproj моего сервиса относительно корня репозитория?
  → Команда: find . -name "*.csproj" (или просто посмотри в репозиторий)

- [ ] Какую конфигурацию собирать? Release (продакшн) или Debug?
  → Для CI обычно Release.

- [ ] Куда dotnet кладёт артефакты? (-o build/output или стандартный bin/Release/net10.0/publish/)
  → Определяет, что указывать в artifacts: paths.

- [ ] Какой runner доступен в моём GitLab?
  → Settings → CI/CD → Runners. Есть shared runners? Есть специфичные с тегами?
  → Если есть только specific runners с конкретными тегами — нужно добавить tags: в джоб.

- [ ] Есть ли у раннера доступ к интернету?
  → Нужно для скачивания Docker-образа и NuGet-пакетов.
  → Если нет — нужен внутренний NuGet-feed и локальный registry образов.

- [ ] Нужна ли аутентификация для NuGet-пакетов (например, корпоративный feed)? → Да → нужна переменная NUGET_AUTH_TOKEN в Settings → CI/CD → Variables.
### Типичные ошибки и как их исправить

**Ошибка: `This job is stuck, because the project doesn't have any runners online`**

- Причина: нет доступных раннеров.
- Решение: проверь Settings → CI/CD → Runners. Если раннеры есть, но джоб не берётся — возможно, в джобе указан тег `tags:`, которого нет у раннера.

**Ошибка: `image not found` или долгое скачивание образа**

- Причина: раннер не может достучаться до `mcr.microsoft.com`.
- Решение: уточни у DevOps-команды, есть ли внутренний Docker registry с образом .NET SDK.

**Ошибка: `error MSB1003: Specify a project or solution file`**

- Причина: неверный путь к `.csproj` или команда запускается не из той директории.
- Решение: укажи полный путь от корня репозитория. GitLab runner клонирует репозиторий и устанавливает рабочей директорией его корень.

**Ошибка: пакеты скачиваются каждый раз, кэш не работает**

- Причина: не задана переменная `NUGET_PACKAGES`.
- Решение: убедись, что `NUGET_PACKAGES: "${CI_PROJECT_DIR}/.nuget"` объявлена, и путь `.nuget/` совпадает в `cache: paths`.

**Ошибка: `only` и `rules` использованы вместе**

- GitLab выдаст ошибку валидации. Используй только одно: либо `rules`, либо `only/except`.

**Ошибка: YAML-синтаксис (табы вместо пробелов)**

- Симптом: `jobs:build config should implement a script: or a trigger: keyword`.
- Решение: настрой редактор (VS Code) на «отступы пробелами» для YAML-файлов, используй GitLab CI Lint.

### Как протестировать пайплайн перед публикацией

**Шаг 1: Валидация синтаксиса** Открой в GitLab: `CI/CD → Editor`. Вставь содержимое файла, нажми `Validate`. Получишь:

- Синтаксические ошибки с указанием строки.
- Визуализацию пайплайна (граф стадий и джобов).

**Шаг 2: Тестирование на отдельной ветке**

```bash
git checkout -b ci/test-pipeline
# Создай .gitlab-ci.yml
git add .gitlab-ci.yml
git commit -m "ci: add build pipeline"
git push origin ci/test-pipeline
```

Временно измени `rules` чтобы пайплайн запустился:

```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "ci/test-pipeline"'
```

Смотри результат в GitLab: CI/CD → Pipelines.

**Шаг 3: Разбор логов** Кликни на джоб → увидишь полный лог выполнения команд. Ищи:

- Красные строки с ошибками.
- Предупреждения dotnet.
- Успешное завершение: `Job succeeded`.

**Шаг 4: Проверка артефактов** После успешного запуска: CI/CD → Jobs → кнопка "Download artifacts". Убедись, что внутри архива именно то, что ожидал.

**Шаг 5: Верни rules обратно**

```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main"'
  - if: '$CI_COMMIT_BRANCH == "dev"'
```

Влей ветку в dev или main — убедись, что пайплайн запустился.
## Часть 5. Расширение пайплайна: test и deploy

### Добавление стадии `test`

```yaml
stages:
  - build
  - test        # ← добавляем

# Джоб теста — запускается после build
run-tests:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:10.0

  # Берём артефакты из build-job (необязательно, если тестируем исходники)
  needs:
    - build-service

  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_BRANCH == "dev"'

  script:
    - dotnet test src/MyService.Tests/MyService.Tests.csproj
        -c Release
        --no-restore
        --logger "junit;LogFilePath=test-results.xml"

  # Сохраняем отчёт о тестах — GitLab умеет их отображать
  artifacts:
    when: always     # Сохранять даже если тесты упали (чтобы видеть, что упало)
    reports:
      junit: test-results.xml
```

После этого в GitLab появится вкладка **Tests** в пайплайне с детальным отчётом по каждому тест-кейсу.

### Добавление стадии `deploy`

Простейший деплой — копирование артефактов на сервер через SSH:

```yaml
stages:
  - build
  - test
  - deploy      # ← добавляем

deploy-to-staging:
  stage: deploy
  image: alpine:latest

  # Только вручную, только из main
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual    # Кнопка в UI

  before_script:
    - apk add --no-cache openssh-client
    # SSH-ключ берём из секретной переменной GitLab
    - eval $(ssh-agent -s)
    - echo "${SSH_PRIVATE_KEY}" | ssh-add -
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh

  script:
    - scp -r build/output/ user@staging-server:/opt/myservice/
    - ssh user@staging-server "systemctl restart myservice"
```

`SSH_PRIVATE_KEY` — переменная из Settings → CI/CD → Variables (тип: File, флаг Masked).

### 5.3 Итоговая структура расширенного пайплайна

```
git push → main
              │
         ┌────▼────┐
```
